# v1.0.3 范围确认：投研工作台与独立投研分析

> 状态：本地实现完成，待验收/发布审批。本文件记录用户确认的产品边界；不授权版本元数据变更、远端发布或真实 Drive 操作。

## 1. 产品边界

v1.0.3 包含两个解耦的能力：

- **深度研究**（显示名“深度研究”，机器标识 `deep-equity-research`）：从零形成可审计研究包、估值、技术证据引用和条件式交易方案。
- **投研分析**（显示名“投研分析”，机器标识 `investment-analysis`）：消费用户明确指定的已有研究 artifact 或 Drive 文档，做轻量增量讨论和交易方案 revision。

投研分析不作为深度研究的内部模式，不给深度研究增加隐式判断字段；两个 skill 只通过标准 artifact 引用和用户显式调用连接。

两个 skill 都不访问账户、持仓、券商或订单，也不执行交易。交易方案属于研究层面的条件描述，最终决定仍由用户作出。

## 2. 交易方案定义

交易方案是可复核、条件化的研究结论，至少包含：

- 多头入场区间和触发条件；
- 目标区间和兑现条件；
- 论点失效/退出条件；
- 默认 1–6 个月波段周期，可由用户显式改选；
- 核心论点、催化剂、反方论证和可证伪条件；
- 入场到失效的下行幅度、潜在收益/风险比和关键风险触发器。

v1.0.3 不做空。方案不依赖用户是否持仓，不输出 `hold/add/reduce/exit` 等持仓状态动作，只输出 `entry_plan`、`target_plan`、`invalidation_plan` 或 `watch`。

只有存在独立观点、反向定价解码、可证伪分歧命题、催化剂/验证节点并通过数据与质量门时，才允许生成 `entry_plan`。财报质量 C/D 级直接否决多头入场方案；它们不自动转换为做空建议。

## 3. Drive 工作台

Drive 的主要用途是跨设备持续记录交易想法和已确认交易方案，不是研究 Markdown 的备份仓库。一个标的/投资案例使用一个主 Google Doc，主文档保留四个核心区块：

1. 交易想法日志；
2. 当前有效交易方案；
3. 证据与决策变更记录；
4. 复盘记录。

完整研报、估值 JSON、技术证据和 HTML 保留在本地；主文档通过链接或 artifact ID 引用它们。每次生成或修改方案、讨论卡或复盘内容后，先展示目标和拟写入内容，得到用户明确确认才写入 Drive。

每个方案使用稳定 `plan_id`，每次调整递增 `revision`，记录父版本、触发证据和变更原因。两个设备基于同一父 revision 各自修改时保留两条 revision，生成冲突摘要，要求用户选择保留、合并或另起方案，不按时间戳静默覆盖。

用户已确认写入但 Drive 暂不可用时，写入可见的本地 outbox，状态标记为“待同步”；重试前重新检查父 revision，不后台自动上传。

## 4. 跨设备与市场偏好

安装器支持时，在安装后询问市场范围；当前宿主不提供可靠 post-install hook 时，在首次调用强制询问。多选项为：

```text
请选择你要覆盖的研究市场（可多选）：
[ ] 美股    [ ] 港股    [ ] A 股    [ ] A/H 对比
```

选择写入每台设备活动工作目录中用户可见、可编辑的偏好文件，包含 `enabled_market_scopes` 和可选的 `default_market_scope`。未设置前不默认美股；明确市场后缀优先，裸代码在多个已启用市场匹配时必须询问。A/H 对比只有在用户选择或明确要求时触发，并自动包含 A 股和港股基础范围。

市场偏好默认按设备保存。研究/交易文档可以通过 Drive 跨设备访问；市场偏好只有在用户明确执行导入/同步时才跟随 Drive。

## 5. artifact 身份与输入

跨市场 artifact 使用三层身份：

- `issuer_id`：同一发行人的稳定身份；
- `listing_id`：具体交易所、代码、币种和上市身份；
- `case_id`：一项投资案例的稳定身份。A/H 对比使用一个 `case_id`，挂载两个 `listing_id`。

投研分析必须接收本地 artifact 路径、Drive 文档链接/ID 或已登记的 `case_id` 作为明确输入。未指定时只查当前工作区已登记 manifest，不扫描整个 Drive 或本地目录。

## 6. 投研分析的轻量约束

投研分析默认只处理用户提供的新材料、指定公告/财报/行情或已有 artifact；不做广泛搜索，不重跑完整研究、估值或技术图表，不自动调用深度研究。它输出讨论卡 Markdown 和结构化 JSON，至少记录：新证据、来源/时间戳、假设变化、论点状态、反方论证、待验证事项、方案 revision（如有）和置信度。

只有用户明确要求或预设升级条件触发时，才提议调用深度研究或技术分析；即使提议，也不自动执行。写入 Drive 仍沿用明确确认规则。

## 7. 研究 Markdown 与阅读视图

Markdown 是规范、可审计、可移植源稿，使用统一元数据、目录、关键数据表、事实/推断/缺口标签、风险和待验证事项。按需从同一源稿生成 `underwriting.html` 阅读视图，加入目录、卡片、折叠区块和图表；HTML 不是第二份手工维护的内容，PDF 不纳入默认流程。

## 8. 已确认的非目标

- 不做空，不连接账户、券商或订单；
- 不记录账户余额、仓位比例或个人风险预算；
- 不把持仓状态加入输入；
- 不自动扫描 Drive、自动搜索外部信息或后台上传；
- 不把完整 Markdown/JSON 自动复制到 Drive；
- 不允许图表或文字创造 JSON/技术证据中不存在的新数值。

## 9. 本地验收主线

验收必须覆盖：市场 onboarding 与歧义路由、深度/财报模式分流、3 年/8 季度基线、可复算估值与终值三查、财报质量 A–D 及 C/D 否决、技术数据失败与区间无交集、条件式交易方案、Drive 确认/outbox/revision 冲突、以及投研分析轻量讨论卡和不自动串联。全部先在离线 fixture 和临时集成分支验证。
