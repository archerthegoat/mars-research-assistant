# v1.0.3 执行与监督计划（已确认规划）

> 本计划供 Kimi 一次性完成实现与自检，完成后由主监督者集中 Code Review。所有工作先保持本地；不推送、不发布、不改 GitHub Issue、不操作真实 Drive 数据。产品边界已通过逐项确认；实现阶段只细化字段和适配器，不得重新打开已决策范围。

## 1. 冻结的版本目标

v1.0.3 保留“深度研究”名称和 `deep-equity-research` 机器标识，目标是将当前通用九章深研替换为可复算、可形成交易方案的买方研究流程，并补齐：

- 首次研究与九章财报更新模式；
- 来源/时间戳/数据对账、财报质量 A–D 与适用时的 Beneish/收入确认检查；
- DCF、反向 DCF、PVGO、概率加权与扩展估值的 JSON 留档和脚本复算；
- 技术面证据编排、价值/入场/失效/目标价格区间和注释图；
- 首次使用时的美股、港股、A 股、A/H 多选市场引导；
- Drive 投研工作台：想法、交易方案、市场思考、周度/案例复盘；
- Markdown 源稿和按需 HTML 阅读视图；
- 十六类行业附录及美股、港股、A 股、A/H/VIE/ADR 的市场扩展合同。
- 独立、轻量的 `investment-analysis`（“投研分析”）skill：讨论卡、artifact 引用和交易方案 revision，不自动串联深度研究。

这些是版本目标。Kimi 可按下列 Batch 顺序组织实现，但不需要等待中间 Code Review；完成后必须一次性提交完整 diff、测试结果和自检报告。任何数据不足、模型未复算或技术质量门失败，都必须输出明确缺口而不是降级成主观结论。

## 2. Kimi 分批执行顺序

### Batch 0：基线与接口冻结

盘点当前运行包、根入口、七个 Skill、离线 fixture 和验证入口；将 v1.0.3 目标转成 capability JSON 草案和测试矩阵。只改文档/合同/fixture，不改运行时行为。

验收：现有 v1.0.2 验证仍通过；所有新增接口有输入、输出、失败关闭和来源字段；实现细节提案与已确认产品边界分开记录。

### Batch 1：首次市场引导

实现根入口首次使用引导和用户可见偏好文件：美股、港股、A 股、A/H 可多选，并允许单次覆盖；歧义 ticker 必须要求范围选择。不得在 Skills CLI 安装命令中假设存在安装后钩子，也不得写 Skill 安装目录的隐藏状态。

验收：未配置时先引导；多选可保存/读取/修改；裸 ticker 和 A/H 配对测试覆盖；用户未选市场时不猜测。

### Batch 2：深度研究替换合同与数据账本

保持 `deep-equity-research` 标识和“深度研究”显示名，建立首次研究/财报更新两种模式、九章结构、至少三年/八季度基线字段、来源账本、市场/币种/会计期间字段和缺口状态。为所有 artifact 固定 `issuer_id`、`listing_id`、`case_id` 和版本字段。

验收：输入不完整时不创建伪完整报告；来源和 `as_of` 可逐项追溯；财报更新与无旧模型首次覆盖分别有 fixture。

### Batch 3：估值深模块

在清晰 seam 后实现 `scripts/dcf.py` 和 JSON schema。先完成三情景概率加权 DCF、反向 DCF、PVGO/预期差表和终值三查，再接入 EPV/EVA/剩余收益/SOTP/蒙特卡洛适配器。脚本计算结果不能由语言模型补写。

验收：每个模型有成功、缺口、非法输入和可复算 fixture；模型版本、假设来源和结果完整留档；缺参数时不输出公允价值数字。

### Batch 4：财报质量与决策门

实现应计质量、Beneish（适用性门）、收入确认红旗、现金流、审计/治理信号和 A–D 规则。C/D 对多头方案触发确定性否决；不能把 C/D 自动变成做空建议。

验收：适用/不适用/未获取到三种状态可区分；C/D 方案不会生成买入交易计划；每个等级有可追溯证据和规则解释。

### Batch 5：技术证据组合与交易方案

通过现有 `technical-analysis` 的 `evidence_id` 消费已完成日线、ATR、均线、支撑/阻力和条件情景；不改写原技术证据。新增 trade-plan JSON 和临时注释 HTML，由规则生成价值、入场、失效和目标区间。

验收：技术质量门失败、证据过期或价值/技术无交集时不生成价格区间；合格 fixture 的 Markdown、JSON、HTML 数字完全一致；图表不引入额外行情或主观价位。

### Batch 6：多市场与行业模块

先完成市场选择、身份核验、币种/汇率/交易日历、A/H 对比、VIE/ADR 结构风险的公共接口，再按行业模块逐一实现十六类 KPI/预测/估值/反证配置。不得用“行业文字附录”冒充模型差异。

验收：每个市场和行业模块至少有输入契约、数据缺口和一个离线验收场景；不支持的 provider 或字段明确失败，不能静默 fallback。

### Batch 7：Drive 工作台与呈现层

在不自动操作真实 Drive 的前提下，先实现一个标的/案例一个主文档的想法、当前方案、证据/决策变更、复盘区段，以及提议/回执/读取、`plan_id + revision`、outbox 和冲突合同的离线 fixture；研究 Markdown 使用统一阅读模板，按需生成 `underwriting.html`。真实写入仍需独立确认和读回核验。

验收：跨设备读取路径有模拟 fixture；不会覆盖用户手工区段；Markdown 是源稿，HTML 只展示已有数据；初始化与写入授权不互相继承。

### Batch 8：独立投研分析 skill

新增 `investment-analysis`（“投研分析”）独立入口与最小合同：明确 artifact/Drive/case 输入、讨论卡 Markdown + JSON、证据增量、论点状态、反方论证、待验证事项和交易方案 revision。默认不广泛搜索、不重跑研究、不自动调用其他 skill；写入 Drive 仍走确认、revision、outbox 和冲突合同。

验收：未指定输入时拒绝隐式全库扫描；轻量 fixture 不调用深度研究；讨论卡能引用既有 artifact 并生成 revision；没有增量证据时输出“维持原方案/暂无动作”。

### Batch 9：组合级集成与性能

新增 `investment-analysis` 独立入口和 Ask Mars 推荐，更新根入口编排、运行包清单、验证脚本、性能预算和安装集成检查。确认旧快览、技术面、Drive 和独立分析的边界没有被新深度研究吞掉。

验收：完整验证入口通过；所有已有 fixture 不回归；新增报告和方案均唯一命名且不覆盖；运行包不含开发测试材料或预建环境。

## 3. Kimi 完成后的交付格式

全部 Batch 完成后一次性报告：

1. 完整修改文件和接口变更；
2. 全部验收项、未完成项和已知缺口；
3. 执行过的测试命令及完整结果；
4. 自检结论、假设和未实现项；
5. `git diff --check` 与工作区状态。

Kimi 不得自行改变版本号、公开标签、远端分支、Release、GitHub Issue 状态或真实 Drive 内容。遇到未决选择必须暂停并回报，不以默认值扩大范围。

## 4. 主监督者的一次性 Code Review

Kimi 完成全部实现和自检后，主监督者只进行一次集中 Code Review，使用 Matt Pocock 工程流中的标准与规格双轴：接口是否足够深、计算是否集中在可测试模块、失败关闭是否明确、fixture 是否覆盖真实用户可见行为、旧版本是否回归，以及改动是否仍属于 v1.0.3。

Review 结果统一输出为阻塞问题、非阻塞建议和通过项；如有阻塞问题，再由 Kimi 集中修复并重新提交完整 diff，之后进行针对修复的复核。通过后才形成版本验收报告，再等待用户决定本地提交、合并或其他后续动作。

## 5. 当前执行前提

产品决策已确认，Kimi 可以按 Batch 0–9 顺序执行。以下仅作为实现阶段的提案项，不能改变已确认边界：十六类行业注册表的具体名称、JSON 字段级 schema、数据源适配器细节、预注册规则配置格式，以及 Drive 本地模拟协议。任何需要扩大范围的变化必须暂停并回报主监督者。
