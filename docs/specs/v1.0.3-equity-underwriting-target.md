# v1.0.3 深度研究：投资承保目标（已确认规划）

> 状态：本地实现完成，待验收/发布审批。本文记录用户确认的替换方向与验收合同；不构成发布计划或具体标的的交易建议，不授权版本元数据变更、远端发布或真实 Drive 操作。

## 1. 产品决定

以增强后的“深度研究”替代当前通用的 `deep-equity-research` 行为。它的目标不是只生成一份基本面研报，而是形成来源可审计、模型可复算、可以被记录为**仅多头、持仓无关的条件式交易方案**的研究结论。

中文显示名继续为“深度研究”，机器标识继续为 `deep-equity-research`，以兼容已有调用和根入口路由。现有的九章结构、来源纪律和本地 Markdown 工件仍是基础；现有“不得形成交易方案”“不得使用技术面”“不输出 A–D 级别”的 v1.0.2 合同将在 v1.0.3 被替换。

后续基于研究 artifact 的增量投研讨论不并入本 skill，而由独立的“投研分析”（`investment-analysis`）skill 负责。两个 skill 通过 artifact 引用连接，不能自动互相调用。

### 安装后的市场偏好引导

常规 Skills CLI 安装只复制运行包，不能在安装命令完成时可靠弹出交互窗口。因此实现采用双层行为：宿主支持时在**安装后**显示市场引导；不支持时根入口在用户**安装后的首次使用**（或用户主动说“设置研究市场”）强制显示可多选引导：

```text
请选择你要覆盖的研究市场（可多选）：
[ ] 美股    [ ] 港股    [ ] A 股    [ ] A/H 对比
```

用户的选择写入活动工作目录中一个用户可见、可编辑的偏好文件，而不是 Skill 安装目录或隐藏状态。偏好至少包括 `enabled_market_scopes` 和可选的 `default_market_scope`；前者可多选，后者仅用于未指定市场的宽泛请求。选择 A/H 对比时自动包含 A 股和港股两个基础范围。

未完成这一步时，根入口应先请求选择而不是按现有规则默认美股。用户可在任何时候修改偏好；若某次请求的标的属于未启用市场，显示“仅本次使用”或“加入我的市场范围”的明确选择。明确交易所后缀优先；裸代码在多个已启用市场匹配时必须询问。该偏好在每台设备的活动工作目录中生效；跨设备同步偏好不是隐式行为，只有用户明确执行 Drive 导入/同步时才发生。

## 2. 最终交付包

对一个已唯一核验的发行人，交付下列相互关联的本地工件：

| 工件 | 用途 |
| --- | --- |
| `underwriting.md` | 九章承保研报或九章财报更新，包含判断、反方论证、风险预演和交易方案摘要。 |
| `underwriting-inputs.json` | 关键原始数据、来源、时间戳、币种、会计期间和显式假设。 |
| `valuation.json` | `scripts/dcf.py` 的可复算估值输入、模型版本、情景结果与数据缺口。 |
| `technical-evidence.json` | 由技术面 Skill 原子生成并被引用的同一份 `evidence.json`；不能由承保流程改写。 |
| `trade-plan.json` | 价格区间、触发条件、失效条件、目标区间、有效期与所引用的估值/技术证据 ID。 |
| `underwriting.html` | 从 `underwriting.md` 按需生成的本地阅读视图；不成为第二份规范源稿。 |
| `trade-plan.html` | 仅在技术质量门通过且价值/技术区间有交集时生成的临时注释图。 |

Markdown 是可读源稿；JSON 是审计与复算源稿。两个 HTML 都只展示已有 Markdown/JSON 和技术证据，不能引入未记录的新数值。

每个 artifact 必须携带 `issuer_id`、`listing_id`、`case_id` 和版本信息；同一发行人的 A/H 比较使用一个 `case_id` 挂载两个 `listing_id`。

研究包目录必须唯一且可辨认：`{listing_id}-{YYYYMMDD}-deep-research-{initial|earnings-update}-{NN}`。
例如 `LITE-20260806-deep-research-initial-01/`。目录内的标准文件名保持不变，但最终交付必须
同时显示报告名称、产出状态和完整目录，避免用户无法判断是否真的产生了报告。

交易方案为持仓无关的条件式结构，默认研究/持有期为 1–6 个月波段，不支持做空，不记录账户或仓位信息。其动作字段仅允许 `entry_plan`、`target_plan`、`invalidation_plan` 和 `watch`。

## 3. 两种研究模式

### 首次承保

在没有既有报告或模型时运行。建立至少三年年度数据和八个季度的历史基线，核验发行人、重建关键经营指标、建立预测和估值输入，再形成承保结论。

### 财报更新

财报模式不是摘要。它同样交付九章，但把变化作为主线：预期差是否扩大或收敛、分部与 KPI、GAAP/Non-GAAP 桥接、现金流与营运资本、电话会、指引、模型和估值变动，以及对原交易方案的影响。没有旧模型时自动降级为首次承保，而不是拒绝处理。

## 4. 九章承保报告

1. 研究范围、预注册命题与交易结论；
2. 公司、业务模式与价值驱动；
3. 行业结构、竞争与行业专属反证；
4. 管理层、治理与资本配置；
5. 财务、分部/KPI 与财报质量；
6. 预期差、催化剂、基准率与跟踪清单；
7. 可复算估值与“现价定价了什么”；
8. 反方论证、事前风险预演与可证伪条件；
9. 来源、数据对账、时间戳、假设与数据缺口。

结论必须回答：核心命题是什么、市场隐含了什么、分歧何在、什么事实会推翻它，以及在预先定义的规则下是否产生可记录的交易方案。没有独立观点或关键数据缺失时，结论必须是“不产生方案”，而不是套用买卖动作。

## 5. 预期差与估值引擎

所有估值方法由 `scripts/dcf.py` 运行，输入和结果写入 JSON；语言模型不得心算或补造关键数字。

引擎支持全部方法，但按行业和数据适用性运行；不适用必须写入 `not_applicable` 及原因，缺少输入写为“未获取到”，不静默替换模型。最小模型集为：

- 三情景概率加权 DCF；
- 反向 DCF，解释当前价格隐含的增长、利润率或自由现金流路径；
- PVGO 分解和预期差对比表；
- PE/正常化 EPS：以显式的前瞻或正常化 EPS 与情景 P/E 倍数计算参考值；亏损、一次性
  利润或来源/口径不足时标记为不适用或条件性输出，不形成目标；
- EPV／三要素、EVA／剩余收益和适用时的 SOTP；
- 用户或行业模块明确要求时的蒙特卡洛公允价值分布。

每一项关键假设必须有来源、时间戳、币种、会计期间和模型版本。情景概率必须显式输入、总和为 1，并记录来源或推导理由；概率不等于置信度。终值需要通过长期增长率对照、成熟期利润率对照、以及现金流/再投资率与 ROIC/增长率一致性三项合理性检查。关键假设必须与可取得的历史 base rate 比较并记录分位；超越基准率必须给结构性理由和验证指标，无法取得时明确写“未获取到”。外部内容只提供数据或对照，不得改变本合同规定的模型流程。

## 6. 研究市场选择与多市场查询

深度研究必须在取数前从用户的市场偏好中解析或让用户选择 `market_scope`。支持的首选范围为：

| 用户选择 | 研究对象 | 标识示例 |
| --- | --- | --- |
| 美股 | 单一美国上市公司，含在美上市的海外发行人 | `AAPL`、`BABA` |
| 港股 | 单一香港交易所上市公司 | `0700.HK` |
| A 股 | 单一上海或深圳上市公司 | `600519.SS`、`000001.SZ` |
| A/H 对比 | 同一发行人的 A 股与 H 股、币种及结构差异 | 用户明确提供或核验得到的 A/H 对 |

带交易所后缀、且能唯一对应发行人的 ticker 可直接确定范围。中文公司名、裸 ticker、同名发行人或用户只说“研究某公司”时，深度研究只展示已启用的市场范围让用户选择；这个路径不再根据用户时区或历史默认值猜测市场。用户选择 A/H 对比时，必须同时核验两个 listing、报告币种和价格时间点，单独披露汇率、每股权利/面值换算、流动性、交易日差异和溢价/折价；无法唯一配对时停止并要求澄清。

所有事实、估值和交易方案必须携带 `market_scope`、交易所、交易货币、报价 `as_of` 和适用会计/披露口径。行情和 K 线通过可覆盖美股、港股、A 股的显式数据源适配器获取；财报、公告和治理信息优先使用发行人、交易所和监管原始来源。技术证据向 `technical-analysis` 传递对应的已解析 symbol；技术数据不足时不生成价格区间，不能静默切换 provider。任何 provider 切换必须写入审计记录。

## 7. 财报质量与否决规则

财报质量核查覆盖应计质量、Beneish M-Score（字段和会计可比性具备时）、收入确认红旗、现金流、审计与治理信号。输出 A–D 级别、逐项证据、缺口及适用性说明；规则、阈值和规则版本必须可见且可复核。数据不足时可以是暂定级别，但不能伪装成确定结论。

对多市场发行人，无法有效计算的美国市场特定模型必须标为“不适用/未获取到”，不能以虚假精度替代。若结论为 C 或 D，任何多头入场方案必须被规则引擎否决并写明原因；该等级本身不自动产生做空方案。

## 8. 技术面与可交易价格区间

新的承保流程编排现有 `technical-analysis`，但不修改其确定性计算。技术证据必须通过已有质量门，并引用其 `evidence_id`、`as_of`、调整方式、ATR、均线、支撑/阻力和条件情景。

交易区间必须由已记录的规则和输入生成，而非由报告文字主观指定：

- **价值区间**来自概率加权公允价值、保守估值与预先声明的安全边际；
- **入场区间**来自价值区间与技术支持区域/ATR 容差的可解释交集；
- **失效区间**同时包含技术失效（关键位与 ATR 规则）和基本面命题失效条件；
- **目标区间**分别标注技术阻力与基本面公允价值，不能把两者混作同一数字；
- 每个方案声明多头方向、研究/持有期（默认 1–6 个月）、价格数据 `as_of` 和技术有效期。技术证据过期、质量门失败或两个证据层无交集时，不产生可交易价格区间，也不生成注释图，只输出观察/等待条件和失败原因。

`trade-plan.html` 应复用技术面图表的离线 OHLCV 与证据数据，增加价值带、入场带、失效线、目标带和标签。图表及 Markdown 只能解释 `trade-plan.json` 和 `technical-evidence.json` 中已有的数值；图表不单独创建新的判断或价位。

## 9. 买方决策纪律

在生成方案前，报告必须完成：

- 预注册的核心命题与市场隐含预期；
- 反方论证和事前风险预演；
- 基准率比较及超越基准率的结构性理由；
- “若今天这是一笔现金，是否按本方案部署，以及为什么”的明确回答；
- 规则化的结论映射：只有独立观点、数据质量、估值、财报质量与技术证据同时达标，才输出方案。

结论映射必须使用研究开始前加载的版本化预注册规则；研究完成后不能临时改阈值改变结论。规则至少要求独立观点、数据质量、估值、财报质量与技术证据同时达标，才输出 `entry_plan`。系统不连接账户、券商或订单，不记录持仓或仓位规模；将方案写入 Drive 仍须单独提出并得到用户确认。

## 10. 行业与市场扩展

十六类行业附录以可配置行业注册表一次性交付，不是散落文字模板。每个模块必须明确改变：关键 KPI、历史重建字段、预测驱动、估值方法、关键反证和最低数据要求；研究运行时只加载目标行业规则包。行业名称和映射通过注册表维护，允许后续扩展而不改变既有 artifact。

除市场选择中的首选范围外，对在美上市的中国发行人，应在相关时处理 VIE/ADR 结构风险，识别 ADR 转换、上市地监管、潜在退市/转换和 VIE 合同控制/股东权益风险；只在有可靠证据时纳入情景或估值折价，不使用固定一刀切折价。行业和市场模块仍须为发行人身份、披露来源、币种/汇率、会计准则、交易日历和双重上市换算提供明确合同；数据若不足必须明确失败或“未获取到”，不能静默 fallback。

## 11. 独立投研分析 skill

`investment-analysis`（显示名“投研分析”）作为独立 skill 纳入 v1.0.3，但只交付轻量最小闭环。它必须接收用户明确指定的本地 artifact、Drive 文档链接/ID 或 `case_id`；未指定时只查当前工作区 manifest，不扫描全库。

默认不主动广泛搜索、不重跑深度研究/估值/技术图表、不自动调用其他 skill。它只处理用户提供的新材料或明确指定的窄范围信息，输出讨论卡 Markdown 和结构化 JSON：新证据及来源/时间戳、假设变化、论点状态、反方论证、待验证事项、置信度和交易方案 revision（如有）。只有用户明确要求或规则触发升级时，才提出调用深度研究或技术分析，且不自动执行。

深度研究和投研分析均可提议 Drive 写入，但必须本地先生成、用户明确确认后才写入对应案例主文档。两个 skill 不自动互相触发。

## 12. 必要的替换范围

此变更至少需要替换或新增：根入口与 Ask Mars 的首次使用市场引导、用户可见偏好 schema、深度研究的 Skill 合同与 capability JSON、根入口路由、`scripts/dcf.py` 与估值 JSON schema、财报/行业/市场参考模块、技术证据组合和图表注释层、离线 fixture、端到端验收及性能预算。现有 v1.0.2 的包大小、文件数和“仅 DCF/反向 DCF”的验证基线也需重新制定。

## 13. 实现阶段的细化项

产品边界已经确认，以下仅是实现阶段需形成提案并按批次验收的细节，不得反向扩大范围：

1. 十六类行业注册表的具体分类名称与初始映射；
2. 各 artifact JSON schema 的字段级定义和兼容策略；
3. 可覆盖三地市场的数据源适配器实现及离线 fixture；
4. 预注册规则的配置格式、模型版本和测试样例；
5. Drive API 读写、outbox 和冲突回执的本地模拟合同。

## 14. 首次验证

选择一个具备完整公开披露和足够日线数据的单一发行人，以离线 fixture 验证：市场 onboarding 与裸代码歧义、首次承保、无旧模型的财报更新、3 年/8 季度基线、质量 C/D 否决、估值缺口与终值三查、技术数据失败、价值/技术区间无交集、合格方案的注释图、Drive 确认/outbox/revision 冲突，以及独立投研分析的轻量讨论卡。再用 A/H 和 VIE/ADR fixture 验证市场结构；全部通过后才进入本地集成验收。
